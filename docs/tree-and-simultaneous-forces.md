# Дерево модели и одновременно действующие силы

Интерфейс имеет три столбца: дерево модели, свойства выбранного элемента, рабочее поле. Два вертикальных разделителя независимо меняют ширину дерева и свойств (мышью или стрелками); ширина рабочего поля меняется соответственно. Результаты остаются снизу, с отдельным горизонтальным разделителем. Изменение размеров не изменяет проект/результат. Заголовки панелей тёмные, поля/группы имеют явные границы, выбранный узел — контрастное выделение; светлая и тёмная темы сохранены.

Ветки «Сварные швы» и «Нагрузки» раскрываются. ПКМ в дереве или Shift+F10 открывает собственное меню «Добавить участок» / «Добавить силу». Добавленный элемент появляется в раскрытой ветке и выбирается для редактирования. Силы F1/F2/… действуют **одновременно внутри активного нагрузочного случая**, каждая имеет собственные Fx/Fy/Fz и приложение в C либо точке P=[x,y,z]. Свободный момент M1 — отдельный узел. Выбор ветки нагрузок открывает обзор; выбор силы/момента — соответствующие свойства. Имеющиеся независимые нагрузочные случаи остаются отдельными задачами и не складываются между собой.

Для старого проекта без `forces` показывается существующая сила F1 из `force_n/application`. При добавлении второй силы или удалении/переименовании первой создаётся явный список. Новая сила нулевая, её значения задаёт пользователь. Силу можно удалить, в том числе последнюю. История/Undo охватывает изменение коллекции. Черновые неконечные значения не превращаются в ноль; расчёт/сохранение блокируются до исправления.

## Контракт и механика

CalculationInput и LoadCase получили необязательный `forces: AppliedForce[]` (0–64). Каждая запись: `id`, `title`, `force_n`, `application`. Идентификаторы непустые, уникальные внутри случая, до 64 байт; title — 1–100 символов. Отсутствующее поле сохраняет прежнюю семантику `force_n/application`. При наличии `forces` прежние `force_n` должны быть [0,0,0], `application={kind:centroid}`; неоднозначный двойной ввод отклоняется `invalid_forces`. Поле `couple_n_mm` остаётся свободным моментом всей задачи.

Rust вычисляет геометрию и центр C, затем FΣ=ΣFi, MC=Mсв+Σ((Pi−C)×Fi). Для сил в C плечо нулевое. Суммы используют компенсацию Neumaier, конечность контролируется; переполнение отклоняется. При FΣ=0 момент не отбрасывается: пара сил может дать чистое кручение/изгиб. Далее используется прежняя номинальная модель для FΣ/MC, с прежними отказами вырожденного сечения. Расчёта механики в JavaScript нет.

CalculationResult для явного списка содержит `resultant_force_n`; полный список и точки сохраняются в input_snapshot. Старые результаты без списка/результирующей читаются без пересчёта. Snapshot validator требует совместного наличия forces/resultant и конечных значений. JSON/SQLite схемы остаются v1/v2; старые читатели, отвергающие неизвестные поля, не смогут открыть новый проект со списком — нужен обновлённый клиент. REST `/api/v1/calculate` и batch используют тот же сервис; OpenAPI описывает расширение. Независимые случаи хранят собственные списки.

На схеме каждая сила имеет точку и подпись, отображается её направление; до расчёта положение C не подменяется средним координат. «Швы + точка P» вписывает все заданные точки. HUD показывает число сил и результирующую только из Rust-результата; при изменении входа она сбрасывается. PDF перечисляет каждую силу/точку, свободный и результирующий моменты; F/A подставляет FΣ, а не нулевое поле legacy. Исходный JSON прилагается как прежде.

Подготовлены аналитические Rust-тесты равномерной суммы 300+300 N→3 MPa при A=200 mm², пары ±100 N на плечах ±50 mm→10000 N·mm при FΣ=0, остатка 1e16+1−1e16=1 и SQLite/JSON round trip. Frontend и Windows native проверяют ПКМ/выбор/два разделителя/силы в случаях, REST проверяет фактический расчёт и OpenAPI. Текущий Windows-прогон ожидается. Нормативная прочность по-прежнему не оценивается.
